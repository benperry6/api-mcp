对应三条修复：

| 编号 | 修复 | 根因 | 用户可见症状 |
|------|------|------|-------------|
| **F1** | 登录 UI 的 `resourceUri` 改为固定裸 URI `ui://cj-mcp/login`，并对 `show_login_form` + `wait_for_login` 同时注入 | 原来带 `?t=<时间戳>_<序号>`，而 `resources/list` 只广播裸 URI，客户端查不到完全匹配项就不渲染；服务端 `handleResourceRead` 用 `startsWith` 前缀匹配「读得到」，掩盖了「渲染不了」 | 登录 UI 一直不展示，而商品/订单 UI 正常 |
| **F2** | `login.html` 补齐 MCP Apps 握手：`_pending` 响应回调 + 规范方法名 `ui/notifications/initialized` | 三处叠加：① `sendRequest` 无响应回调；② 用 `msg.method === 'ui/initialize'` 判断响应，而 JSON-RPC 响应没有 `method` 字段，永不命中；③ 发的名字是 `ui/initialized`，规范是 `ui/notifications/initialized` | Claude App 中登录界面永久 `visibility:hidden`，"已打开但完全看不到" |
| **F3** | 直连 Token 模式下 `logout` / `verify_credentials` 直接拒绝并说明只能换 URL | 该模式认证态来自每请求的 AsyncLocalStorage，服务端无可清除存储；`clearSession()` 清的 `currentSession` 根本不参与鉴权，写入的新 session 也永远读不到 | 报「✅ 已登出」/「登录成功」，实际下一个请求仍以原账号执行 |

## 六、结论与未覆盖风险

**结论：本次改动可以合入。** 全量 154 项通过，修复基线上 3 项失败，0 新增类型错误，构建通过。

以下是**本次没有验证到**的部分，如实列出：

1. **真实客户端 E2E 未做**。F1/F2 的最终验收是"登录界面在 Claude / Cursor / VS Code Copilot 里真的显示出来"。当前测试验证的是**协议契约**（URI 完全匹配、握手消息序列正确），不是真实宿主的渲染结果。建议连上 `CJMCP-test40`（`http://localhost:3009/mcp`）在 Claude 与 Cursor 各走一遍登录流程做人工确认。
2. **F3 未做真实直连 Token URL 的链路验证**。测试通过 mock `getDirectTokenContext` 构造该模式，未起真实 `/mcp/API@{userId}@CJ:{token}` 连接验证端到端行为。
3. **`login.html` 不计入覆盖率数字**。v8 只统计 TS 源码；握手测试是用 `vm` 真实执行页面脚本的行为验证，属于有效覆盖但不体现在百分比里。
4. **10 个存量类型错误未修**，其中 `auth.tool.ts` 的 `SessionData.loginName` 缺失意味着该字段在运行时可能永远是 `undefined`（会静默降级到 `session?.email`）——值得单独确认，但不属本次改动引入。
5. **改动尚未提交**，仅在暂存区。
